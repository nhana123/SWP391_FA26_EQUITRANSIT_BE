# BE-02: explicit compliance workflow

Backend and `EquiTransit_Demo` only. Production `EquiTransit` was not accessed.

## Default rules and checklist initialization

GET `/api/transport-orders/{order}/compliance?phase=PRE_EXPORT` initializes
missing checklists for all three phases when the order is APPROVED,
IN_PREPARATION, CONFIRMED or IN_TRANSIT and an active Specialist is assigned.
Repeated GETs retain requirement IDs and do not change rowversion/history.
Assigned Specialists and owning Customers both use this endpoint.

Use `bootstrap=false` to inspect evidence without creating a checklist.
The internal readiness facade always remains read-only: a phase that has not
been initialized still returns RULE_ASSESSMENT_PENDING. Initialization does not
approve a document or clear any phase.

POST `/checklists` still supports explicit route assessments. Omitting or
providing an empty `transitCountryCodes` list resolves countries from the current
plan's PlanCheckpointNode records for the exact order/revision. Origin,
destination and duplicate countries are excluded. Explicit nonempty country
lists are preserved. Generated checklists synchronize if graph transit changes;
manual checklists remain explicit Specialist assessments.

Missing active rule scopes are provisioned under the legal catalog lock:

| Phase | Default required documents |
| --- | --- |
| PRE_EXPORT | Export Veterinary Health Certificate; Equine Passport / Vaccination Record |
| ARRIVAL | Import Permit & Customs Entry Declaration |
| QUARANTINE_RELEASE | Post-Arrival Quarantine Release Certificate |

Transit permits have separate document type codes for each country and phase.
Uploading a release permit therefore cannot obsolete an export permit's review.
Default rules are labelled workflow templates, with a service-owned source URL;
the assigned Specialist must verify applicable regulations and actual evidence.
They do not claim to reproduce a jurisdiction's current laws.

The physical schema uses `ComplianceRuleVersion.RuleCode` as the rule family;
there is no separate ComplianceRule table or ACTIVE status column. ReviewedAt
and EffectiveFrom/EffectiveTo define effective versions. Seed script
`tools/seed-demo-compliance.sql` creates the four templates for current Demo
routes and can be rerun without duplicate active versions. Existing custom rules
and legal history are retained. Existing manual checklists may need reassessment
when the catalog changes; stale rule snapshots cannot clear a phase.

## One-step upload and submit

POST `/api/transport-orders/{order}/compliance/requirements/{id}/upload-and-submit`
accepts the owning CUSTOMER or the assigned active SPECIALIST. Type and horse
are derived from the requirement, not accepted from client input.

```json
{
  "fileName": "certificate.pdf",
  "contentType": "application/pdf",
  "contentBase64": "<base64 of the actual PDF bytes>",
  "expiresAt": "2027-03-01T00:00:00Z",
  "referenceNumber": "CERT-2027-001",
  "recordVersion": "000000000001A2B3",
  "operationId": "d86b4f63-5acc-4f20-8da3-e24323268814"
}
```

PDF/PNG/JPEG content is inspected using the existing 5 MiB file policy. One
transaction creates the private file, immutable DocumentVersion and Submission,
then saves the retry receipt and audit event. The receipt's entityId is the
submission ID, and fileKey is the opaque content key. Replaying the identical
command returns the same receipt. Changed input or stale versions return409.
File/version/submission writes roll back together.

Migration020 adds nullable DocumentVersion.ExpiresAt for exact UTC expiry.
Legacy dated uploads retain their existing whole-day validity semantics.
One-step uploads use their upload date as the validity start; callers requiring
an explicit issuedDate may continue to use the legacy document upload API.

## Reviews and clearances

Specialist POST `/submissions/{id}/reviews` accepts APPROVED, REJECTED or REVOKED.
REJECTED requires feedback; `notes` and `reason` are aliases for that field.
GET compliance returns each latest submission's effective status, decision,
feedback and `attachment` metadata (fileKey, name, MIME, size, reference and
expiry). Content remains behind the authorized `/compliance/files/{fileKey}` API.
New submissions show SUBMITTED until reviewed; old rejection feedback is retained
in history and does not appear as the new submission's verdict.

Specialist POST `/clearances` still requires command, phase and expiresAt.
All documents must be current, approved, private, unrevoked and unexpired. Missing
required procedures are recorded atomically as SPECIALIST_DOC_CLEARANCE, using
the actual approved file and source `SPECIALIST_DOCUMENT_REVIEW:<ReviewID>`.
This records the Specialist's attestation, not a manufactured government result.
Explicit pending/rejected/revoked/expired authority results remain blockers.
Generated procedures can be renewed after fresh document validation. Clearance
expiry is bounded by all document/checklist/rule/procedure expiries.
